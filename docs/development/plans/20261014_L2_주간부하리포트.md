# 생산 계획 1차 — 주간 계획·부하 (v3 초안, 2026-10-14)

사용자 방향(2026-10-14): 표준은 참고값(하면서 보강), 생산 계획만 **단독 기능**으로 먼저 완성한 뒤 납기·실적과 연결. 4주 전망, 토요일 포함. 현장 적용 전 사용자가 직접 테스트. 설비 탭에 설비 추가 + **근무 체계 설정**. 장기 목적: 실적 입력까지 연결해 납기 대비 실제 생산 확인.

## 1. 공정 단위(작업) 설계
현장 사실: 대부분 단일 공정(표준 기준 1스텝 22품번, 2스텝 49, 3스텝 34, 4스텝 이상 20). H11SDF-2C-10 처럼 #10~#60 으로 분화된 품번이 있고, 한 설비에서 #30#40#50#60 을 이어서 하는 경우도 있다. 실적 시트도 'MRG6-07#20#30', '4PDVN-03#30#40' 처럼 **합친 공정을 하나의 공정명**으로 쓴다.

**제안: 계획 단위 = 작업(op) = 품번 × 스텝 묶음.**
- 작업 키 `op_label` = 품번 + '#' + 스텝들(예 `H11SDF-2C-10#10`, `H11SDF-2C-10#30#40#50#60`, 단일 공정은 `#10` 또는 스텝 없음 `-`). 스텝 목록은 `steps int[]` 로도 저장(정렬·순서 계산용).
- 한 행이 "어느 장비군에서 몇 개를 몇 UPH 로" 를 뜻한다. 스텝이 여럿이어도 한 설비에서 이어서 하면 **한 행(합친 작업)**, 설비가 다르면 **행을 나눈다**. 즉 행 수 = 설비 투입 단위 수. 이것이 설비 부하와 1:1 이라 경우의 수를 전부 덮는다.
- 기본 전개: 표준이 있으면 표준의 공정명 단위로 행 생성(표준에 '#30#40' 처럼 합친 공정명이 있으면 그대로 한 행). 없으면 품번 한 행. 행 편집으로 **합치기**(여러 스텝 행 선택 → 한 행, UPH 참고값 = 1/Σ(1/UPH_i), "추정" 표시)와 **나누기**(합친 행 → 스텝별 행) 지원.
- 같은 품번의 여러 작업은 같은 주에 같은 수량이 기본값이지만 행마다 수량을 달리 적을 수 있다(재공 이월).
- 순서(`seq`)는 표시·향후 흐름 계산용. 1차 부하 계산에는 쓰지 않는다.
- 표준 쪽 영향 없음. 계획에서 쓴 작업 키·UPH·장비군은 나중에 표준 보강 재료(2차).

## 2. 근무 체계·능력 설계 (설비 탭에서 제어)
현장: 평일 주/야 2교대 각 10h, 토요일·공휴일 주/야 2교대 각 6h. 일요일은 휴무(확인 필요).

- `shift_profiles`(day_type PK: WEEKDAY/SATURDAY/HOLIDAY/OFF; day_hours, night_hours) — 기본 10/10, 6/6, 6/6, 0/0. 설비 탭 "근무 체계" 표에서 편집.
- `work_calendar`(cal_date PK, day_type, note) — **예외만 저장**(공휴일, 특별 근무/휴무). 저장이 없으면 월~금 WEEKDAY, 토 SATURDAY, 일 OFF 로 계산. 설비 탭에서 날짜 추가/삭제(공휴일 등록).
- 설비별: `machines.active`, `night_active` 그대로 + **`sat_active`(토·공휴일 가동, 기본 true)** 추가. 설비별 임시 휴지(수리 등)는 2차(설비별 예외 캘린더).
- 능력(장비군, 주) = Σ설비 Σ날짜 [day_hours + night_hours×night_active] × (토·공휴일이면 sat_active). 기존 `shifts`·`hours_per_shift`(9h) 는 설비 스케줄 보드가 쓰므로 남겨 두고 주간 계획은 쓰지 않는다(보드 통합은 2차).

## 3. 화면
- 생산 계획 탭 순서: **주간 계획** · 설비 스케줄 · 공정 표준 · 설비.
- 주간 계획: 주 선택(월~일, 능력은 요일 유형별) → 계획 표(품번·작업(스텝)·장비군·수량·UPH(참고값+출처, 수정 가능)·준비(분)·필요 h·납기(참고)·메모; 행 추가/삭제/합치기/나누기; 품번 검색 추가; [미납 수주에서 가져오기] 제안 버튼은 1차 포함 여부 확인) → 요약(장비군별 필요 h / 능력 h / 부하율, 전후 4주 미니 표) → 저장(주 단위 upsert/delete, nonce).
- 설비: 기존 편집 표 + 설비 추가 폼(ID 중복 검사) + 근무 체계 표(요일 유형별 주/야 시간) + 공휴일·예외일 등록.
- 설명은 `help=` 툴팁만.

## 7. 사용자 결정 (2026-10-14)
1. 일요일 휴무(0h). 공휴일은 토요일과 같이 주/야 6/6.
2. 합친 작업 UPH 참고값 = 1/Σ(1/UPH_i), "추정" 표시 — 승인. 향후 CAM 연동 원가 계산과의 연결성에서도 적합하다는 의견.
3. [미납 수주에서 가져오기]는 1차 제외 — 설비·제품 연결 표본이 적어 고도화 뒤 진행. 1차는 품번 검색 추가만.
4. 설비 탭에서 근무 체계(요일 유형별 주/야 시간)·공휴일 예외·설비별 토·공휴일 가동 제어.

## 8. Reviewer 반영 결정 (v4, 2026-10-14)
Data(BLOCKER 0·HIGH 4·MEDIUM 8)·QA/UX(BLOCKER 1·HIGH 6·MEDIUM 7) 검토 결과 반영:
- **저장 = RPC 한 트랜잭션** `save_week_plan(p_week date, p_fingerprint text, p_rows jsonb, p_delete bigint[])` (QA B1(a), Data HIGH-1 대안). 서버가 fingerprint(count + max(updated_at)) 비교 → 다르면 'stale' 거부. 폴백 없음(RpcUnavailable 도 오류 표시). 앱은 `click_guard("wp_save")`.
- `hours` 는 **생성 컬럼**(qty/uph + setup/60, uph 없으면 NULL) — 앱은 페이로드에 넣지 않음(Data HIGH-4 A, QA H1). 요약에 "UPH 미정 n행(부하 제외)".
- **DB 유니크 제약 없음**(Data MED-1: 같은 작업 복수 행 허용). 대신 앱 검증 `validate_week`: 같은 품번의 스텝 집합 겹침 → 거부, 같은 (pn, op_label, group) 중복 → 경고 표시(QA H2 절충).
- `op_key`(정규화 키: product_id 또는 pn_key + '|' + 정렬 스텝) 컬럼 추가, 괄호 설명 제거·숫자 스텝 전부 추출·한글 스텝은 unparsed (Data MED-3). 실적 공정명 변형 26종 확인(‘#황삭’, ‘#수정#20’, ‘#MCT’, ‘#10.#20’, 괄호 설명).
- 전개 시 표준 `group_code` 가 설비 장비군 집합(CNC·MCT)에 없으면 `machines_used` 첫 설비의 장비군 → 없으면 'ETC' + "장비군 확인" 표시(Data HIGH-2). 표준 테이블은 손대지 않음. `op_std.py:108` 수정은 별도 L2.
- 능력 기준 통일(보드 9h vs 근무 체계)은 **2차** — 1차는 보드·설비 KPI 에 help 로 "보드 능력은 교대당 9h 기준" 명시(Data HIGH-3 최소안). 스텝 없음 표기는 `steps='{}' + op_label=pn` 으로 통일(QA L2·Data MED-2).
- 합친 작업: UPH = 1/Σ(1/UPH_i), 하나라도 없으면 NULL(표준 부족), setup = Σ (QA H5). 나누기: 스텝별 행 각각 전량 qty(QA H5). 편집 UI: 고정 행 + "삭제" 체크 열, 행 추가는 폼 밖 "품번 검색 추가"(즉시 insert 대신 세션 임시 행 → 저장 시 RPC), 합치기는 "스텝" 텍스트 셀 편집, 나누기는 "작업" 선택 열(QA M1). UPH 를 참고값과 다르게 고치면 MANUAL.
- 능력: 일요일 OFF 강제, 일요일+HOLIDAY 등록 거부, `active`·`night_active`·`sat_active` 곱, 능력 0 이면 부하율 "능력 없음"(QA H6, Data MED-8). `shift_profiles` 4행 시드(업무 데이터 아님), `work_calendar.day_type` FK(Data MED-5). 근무 체계 편집은 number_input 8개 폼(QA M5). 설비 추가는 `normalize_machine()` 정규화 + cache=False 중복 검사 + 23505 처리(QA M4).
- 되돌리기 순서: 계획 행 스냅샷 → 코드 revert 먼저 → DROP(items → calendar → profiles → 컬럼). 적용은 migration 먼저, 푸시 나중(Data MED-6).
- 테스트: `tests/test_weekly_plan.py` 순수 함수 16종(QA A-1~16), AppTest B1~B8, 보드 회귀(test_schedule 9h 기대값 유지). 목 fetch 에 `cache` 인자 추가.
- 사용자 직접 테스트 체크리스트: 합치기 후 흡수 행 삭제 누락 → 저장 거부, 두 브라우저 동시 저장 → stale 거부, UPH 미정 행 요약, 공휴일 등록 뒤 능력 변화.

## 9. 구현 리뷰 반영 (2026-10-14, 구현 diff 2차 검토)
- **BLOCKER(Data·QA 공통)**: fingerprint 문자열 형식 불일치(서버 `timestamptz::text` 공백·`+00` vs PostgREST `T`·`+00:00`) → 행이 있는 주는 두 번째 저장부터 항상 stale. 운영 DB 로 형식 차이 확인(`2026-10-14 03:58:04+00` / `2026-10-14T03:58:04+00:00`). **양쪽을 초 단위 정수(epoch)** 로 변경: 서버 `count:sum(id):floor(epoch(max(updated_at)))`, 앱 `updated_epoch()` 파싱. 테스트로 두 형식이 같은 초로 읽힘을 고정.
- QA H-1 합치기 뒤 UPH 가 옛 값 그대로 → `build_payload`(순수 함수)로 저장 페이로드 조립: 스텝이 바뀌면 표준을 '단위'로 조합해 1/Σ(1/UPH) 재추정(EST), 표준이 없으면 UPH 비움 + 경고. H-2 미저장 행 경고(st.warning) + [추가] help. M-1 오류 행 번호 = 표 행 번호.
