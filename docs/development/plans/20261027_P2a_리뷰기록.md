| **I1 수주 라인 대사** | **조건부 적합.** I1a의 INNER JOIN은 회차가 전혀 없는 라인을 제외합니다. 그러나 069/076의 `confirm_shipment`는 회차 부족·미충당을 허용하므로, LEFT JOIN으로 바꾸고 모든 차이를 오류로 처리하는 것도 부적절합니다. 회차 있는 라인의 대사와 회차 미충당 진단을 구분해야 합니다. I1b는 활성 라인의 미납을 `greatest(qty-received_qty,0)`와 비교해야 합니다. `utils/so_close.py:71`의 실제 계산도 이 방식입니다. 076 이후 뷰의 `pending_qty_calc`는 저장된 `pending_qty`를 사용하므로 두 값 비교만으로 독립 검증되지는 않습니다. |
| **I2 확정 전표 충당** | **수정 필요 [H1].** I2a의 `si.qty = Σ충당`은 코드의 필수 보장이 아닙니다. RPC는 충당합이 라인 수량보다 작으면 `unallocated`로 반환하고 확정합니다. 강제 불변식은 `0 ≤ Σ충당 ≤ si.qty`, 충당 수량 양수, 충당 회차와 전표 라인의 `soi_id` 일치입니다. 부족분은 업무 검토 지표로 분리해야 합니다. I2b는 상한 검사로 타당하고, I2c는 이관·도입 전 delivered 기준량을 별도로 인정한 범위에서 타당합니다. |

| **I11 채번 유일성** | **수정 필요 [H8].** I11f는 설명과 다릅니다. W LOT 정규식이 없어 모든 LOT를 검사하며, 서로 다른 자재 수만 세어 동일 자재의 중복 RECEIPT는 놓칩니다. 068의 보장은 `^W[0-9]+$`에 해당하는 RECEIPT의 LOT 번호 유일성입니다. | **I12 매입 연결** | **정보성 지표로 적합 [M4].** I12a의 `cnt`는 미연결 건수가 아니라 mapping_status 종류 수이고, I12b는 미연결 행 수가 아니라 집계된 월 수입니다. “각 SQL 결과 0건이 정상”이라는 공통 설명에서 제외해야 합니다. 월별 표본 순서는 `row_number() over(order by 월)`로 고정해야 합니다. |

### 주요 수정 SQL

아래는 위반 행을 반환하는 핵심 SQL입니다. 초안의 건수·표본 집계 래퍼는 생략했습니다.

**I1b: 실제 미납 계산과 일치**

```sql
SELECT soi_id
FROM sales_order_items
WHERE status NOT IN ('CLOSED','CANCELLED','REPLACED')
  AND abs(
    coalesce(pending_qty,0)
    - greatest(coalesce(qty,0)-coalesce(received_qty,0),0)
  ) > 1e-9;
```

I1a는 회차 없는 라인을 추가 검출하더라도 이를 곧바로 오류로 분류하지 말고, RPC가 허용한 미충당 여부를 함께 보고해야 합니다.

**I2: 강제 보장과 미충당 경고 분리**

```sql
-- 강제 보장: 충당합이 전표 라인 수량을 초과하지 않음
SELECT si.si_id
FROM shipment_items si
JOIN shipments s USING (shipment_id)
LEFT JOIN (
  SELECT si_id, sum(qty) AS q
  FROM shipment_allocations GROUP BY si_id
) a USING (si_id)
WHERE s.status='CONFIRMED'
  AND coalesce(a.q,0) > si.qty + 1e-9;

-- 충당 대상·수량 검증
SELECT a.alloc_id
FROM shipment_allocations a
LEFT JOIN shipment_items si USING (si_id)
LEFT JOIN so_delivery_schedule d USING (sched_id)
WHERE a.qty <= 0
   OR si.si_id IS NULL
   OR d.sched_id IS NULL
   OR d.soi_id IS DISTINCT FROM si.soi_id;
```

`si.qty > Σ충당`은 별도 경고로 유지할 수 있지만, 정상 미충당과 실제 반영 실패를 추가 조사해야 합니다.

**I3: 라인별 ISSUE 순합**

```sql
SELECT s.shipment_id, si.si_id
FROM shipments s
JOIN shipment_items si USING (shipment_id)
LEFT JOIN inventory_transactions t
  ON t.ref_table='shipment_items'
 AND t.ref_id=si.si_id
 AND t.txn_type='ISSUE'
WHERE s.status <> 'CONFIRMED'
GROUP BY s.shipment_id, si.si_id
HAVING abs(coalesce(sum(t.qty),0)) > 1e-9;
```

기존 충당 잔존 검사와 함께 사용합니다. 제품별로 잘못 남은 역분개까지 잡으려면 `product_id`별 검사도 추가해야 합니다.

**I4: RPC 적용 대상의 라인·제품 대사**

```sql
SELECT si.si_id
FROM shipment_items si
JOIN shipments s USING (shipment_id)
LEFT JOIN inventory_transactions t
  ON t.ref_table='shipment_items'
 AND t.ref_id=si.si_id
 AND t.txn_type='ISSUE'
WHERE s.status='CONFIRMED'
  AND si.soi_id IS NOT NULL
GROUP BY si.si_id, si.product_id, si.qty
HAVING abs(
  coalesce(sum(t.qty),0)
  + CASE WHEN si.product_id IS NOT NULL THEN si.qty ELSE 0 END
) > 1e-9
OR coalesce(bool_or(
  t.txn_id IS NOT NULL
  AND (
    t.product_id IS DISTINCT FROM si.product_id
    OR t.material_id IS NOT NULL
  )
),false);
```

正負のISSUEは正しい取消・訂正でも存在するため、単純な `qty<0` 制約には置き換えません。

**I8/I9: 배치의 실제 지시 연결**

```sql
SELECT b.batch_id
FROM wo_batches b
LEFT JOIN wo_tracking w ON w.wo_id=b.wo_id
WHERE b.wo_id IS NOT NULL
  AND (
    w.wo_id IS NULL
    OR b.wo_number IS DISTINCT FROM w.wo_number
    OR b.product_id IS DISTINCT FROM w.product_id
    OR b.w_lot IS DISTINCT FROM w.w_lot
  );
```

`wo_id IS NULL` 레거시는 별도 모호성 목록으로 출력해야 합니다. 번호만으로 자동 귀속시키면 안 됩니다.

**I10i: WO 정상 상태 포함**

```sql
SELECT wo_id, status
FROM wo_tracking
WHERE coalesce(status,'') NOT IN
  ('IN_PROD','OUTSOURCE','REWORK','INSPECT','DONE','CLOSED');
```

I10d의 “CANCELLED 수주 + 확정 출고 존재”는 강제 불변식에서 제거하고, 취소 수주의 활성 미납·종결 수량 불일치를 검사하는 것이 맞습니다.

**I11f: 068과 동일한 W LOT 범위**

```sql
SELECT lot_number, count(*) AS receipt_count
FROM inventory_transactions
WHERE txn_type='RECEIPT'
  AND lot_number ~ '^W[0-9]+$'
GROUP BY lot_number
HAVING count(*) > 1;
```

**I13: 종결·취소 수량 및 비활성 미납**

```sql
SELECT soi_id
FROM sales_order_items
WHERE (
  status IN ('CLOSED','CANCELLED')
  AND abs(
    greatest(coalesce(qty,0)-coalesce(received_qty,0),0)
    - coalesce(closed_qty,0)
  ) > 1e-9
) OR (
  status IN ('CLOSED','CANCELLED','REPLACED')
  AND abs(coalesce(pending_qty,0)) > 1e-9
);
```

기존 CANCELLED 레거시에는 별도 baseline 분류가 필요합니다.

**I14c: 동일 자재의 입고 LOT 확인**

```sql
SELECT w.wo_id
FROM wo_tracking w
WHERE nullif(btrim(w.w_lot),'') IS NOT NULL
  AND NOT EXISTS (
    SELECT 1
    FROM inventory_transactions r
    WHERE r.txn_type='RECEIPT'
      AND r.lot_number=w.w_lot
      AND r.material_id=w.material_id
  );
```

I14a/b는 수동 생산보고와 현장 LOT 투입 경로를 구분한 뒤 적용해야 합니다. `ref_table='production_log'`를 제외한다면 제외 건수도 따로 보고하여 추적 공백을 숨기지 않아야 합니다.

**I16b: 기존 계산의 NULL 기본값 반영**

```sql
SELECT b.bom_id
FROM bom b
JOIN products p USING (product_id)
WHERE p.archived_at IS NULL
  AND coalesce(b.process_type,'MATERIAL')='MATERIAL'
  AND (
    b.qty_per_pc <= 0
    OR coalesce(b.shared_factor,1) < 1
  );
```

NULL `qty_per_pc`를 금지할지는 별도 필수입력 정책으로 정해야 합니다. 앱은 일부 계산에서 이를 1로 해석합니다.

**I17: KST 업무일 명시**

```sql
SELECT shipment_id, ship_date
FROM shipments
WHERE status='CONFIRMED'
  AND ship_date >
      (current_timestamp AT TIME ZONE 'Asia/Seoul')::date;
```

도입 경계의 timestamptz도 업무 기준 시간대를 확정한 뒤, 예를 들어 `'2026-09-05 00:00:00+09'::timestamptz`처럼 명시해야 합니다.

## 3. P0/P1/P2 재검토

### I11d 중복 wo_number

**현재 governance의 I11=P0 규칙에 따라 P0를 유지해야 합니다.** reviewer 판단만으로 하향할 수 없습니다.

더구나 “종결됐고 제품 JOIN도 하므로 무해”라는 설명은 근거가 부족합니다.

- `wo_tracking`의 초기 UNIQUE는 `(wo_number,w_lot)`입니다.
- 배치 조회에는 `wo_number` 단독 필터가 있습니다.
- 061 `product_lot_stock_v`는 `(wo_number,product_id)`로 JOIN합니다.
- baseline에는 **동일 번호·동일 제품·다른 W LOT** 사례가 있습니다.

따라서 결과 행 증식과 추적 대상 혼동 가능성을 조사해야 합니다. 과거 예외를 승인하더라도 해당 ID만 등록하고 신규 중복 검사는 유지해야 합니다.

### I17 미래 납품일 확정

**현재는 P1 정책 경고가 적절합니다.** 미래 납품일 확정을 현재 앱이 허용하므로, 이를 기존 코드 보장 위반이라고 설명하면 안 됩니다.

관련 재고 뷰는 미래 `txn_date`를 제외하지 않고 합산합니다. 따라서 미래 납품일 ISSUE도 현재 화면 재고에 반영됩니다. 실사 기준과 충돌할 수 있다는 문제 제기는 유효하지만, 이를 금지하려면 새로운 사용자 결정과 서버 검증이 필요합니다.

### 그 밖의 등급

- **I2a 미충당:** 정상 허용 흐름까지 포함하므로 전부 정합성 P1로 묶지 말고, 업무 경고와 실제 반영 실패를 분리합니다.
- **I3/I4:** 수정된 라인·제품별 대사 실패는 P0 취지에 맞습니다.
- **I10 정상 INSPECT 및 취소 수주 이력:** 위반이 아닙니다.
- **I16 복수 자재 BOM:** 별도 정책이 없는 한 위반이 아닙니다.
- **I12:** P2 통계이며 “0건 정상” 대상이 아닙니다.

공통 `0.5` 허용오차는 기존 DQ 뷰와 맞지만 RPC는 주로 `1e-9`를 사용합니다. 구조적 수량 대사에 0.5를 쓰면 작은 실제 오류를 놓칠 수 있습니다. 품목·단위별 허용오차와 RPC 수준 정합성 오차를 구분해야 합니다.

## 4. 추가할 불변식

### 4.1 batch_links 수량·소유권·순환

우선 추가할 항목은 다음과 같습니다.

- `qty>0`, 부모≠자식, 유효한 link_type.
- 부모·자식의 동일 지시 소유권.
- MERGE 부모의 상태와 연결 수량.
- DAG 순환 금지.

**현재 부모 qty = 자식 qty 합**이라는 단순식은 잘못입니다. `_bat_take()`는 SPLIT 시 부모 qty를 감소시키고 자식과 링크를 만듭니다(`streamlit_app.py:18899~18940`). MERGE 자식도 이후 다시 분할되어 현재 qty가 감소할 수 있습니다.

따라서 보존 검증은 생성 당시 수량 또는 후속 SPLIT 유출량까지 포함해야 합니다. 완전한 생성 스냅샷이 없는 경우 검증 가능한 범위를 명시해야 합니다.

### 4.2 wo_tracking 누적값과 wo_events

추가할 가치가 있지만 단순 `SUM(event.qty)` 대사는 부적절합니다.

- INSPECT 세부 수량은 `detail.pass/tokusai/rework/scrap/return/output`에 있습니다.
- INPUT_CANCEL·INSPECT_CANCEL·STEP_CANCEL을 역반영해야 합니다.
- 최초 INPUT 이벤트에는 `wo_id`가 없는 경로가 있습니다.
- `_wo_apply()`는 누적값·원장·이벤트를 별도로 기록하며 이벤트 실패를 경고하고 진행합니다.

이벤트 도입 전 기준량과 대상 식별 방법을 정한 뒤 검증해야 합니다. 이벤트 미기록 자체도 추적성 경고로 분리할 필요가 있습니다.

### 4.3 so_line_replacements

과거 `closed_pending_qty`를 현재 미납과 직접 비교하면 이후 정정 때문에 오탐이 생길 수 있습니다.

## 2. 신규 발견 사항

### HIGH

**N1. 예외 J는 거래처별 업무 규칙을 전체 전표 면제로 확대할 위험이 있음 — §5-J, §8 I17**

J는 특정 거래처 요청을 근거로 하지만 조건에는 거래처 제한이 없습니다. 그대로 구현하면 모든 거래처의 “25일 이후 확정 + 다음 달 1~5일 납품일”을 정상으로 간주합니다. 실제 선확정 오류도 숨길 수 있습니다.

또한 I17b는 모든 원장 유형을 조회하므로, J 적용은 해당 전표에 연결된 `ISSUE / ref_table='shipment_items' / ref_id=si_id`로 한정해야 합니다. 069 RPC도 이 연결을 기록합니다. 승인된 거래처·전표 범위와 확인된 실물 출고 조건을 명시해야 합니다.

### MEDIUM

**N2. I21은 ‘교체 → 복원 → 재교체’ 정상 이력을 오탐함 — §8 I21**

복원된 과거 REPLACE 행마다 현재 원라인이 REPLACED인지 검사합니다. 동일 원라인을 정상적으로 다시 교체하면 과거 복원 이력이 위반으로 반환됩니다. `_rp_apply`는 새 이력을 추가하고 `_rp_revert`는 기존 이력에 `reverted_at`을 남기므로 가능한 경로입니다(`streamlit_app.py:6568, 6688`).

현재 관계는 활성 REPLACE 이력과 비교하고, 복원 이력은 이후 재교체 여부를 고려해야 합니다.

**N3. I18a의 `wo_number` 단독 합산은 제품 간 오류를 상쇄하고 원장 단독 행을 누락함 — §8 I18a**

WO 번호 충돌을 별도 검출하면서 생산 수량은 같은 번호 전체를 합칩니다. 서로 다른 제품의 과대·과소 반영이 상쇄될 수 있습니다. 또한 지시 집합에서 LEFT JOIN하므로 대응 지시가 없는 PROD_OUTPUT은 검사되지 않습니다.

검사 완료 원장은 `product_id`와 `work_order`를 함께 기록합니다(`streamlit_app.py:19614, 20105`). 최소 `(wo_number, product_id)`로 양쪽을 집계하고, 대응 지시 없는 원장도 별도 반환해야 합니다.

**N4. I10d의 `sales_orders.updated_at`은 비활성 전환 시각이 아님 — §8 I10d**

077 종결 RPC는 이를 갱신하지만 교체 처리의 CANCELLED 변경은 갱신하지 않습니다(`streamlit_app.py:6568`의 `_rp_apply`). 따라서 정상적인 교체 전 출고가 생성 시각과 비교되어 오탐될 수 있습니다. 일반 갱신 시각을 비활성 전환 시각으로 간주하는 정의는 성립하지 않습니다.

정확한 전환 시각을 확보하기 전에는 이 검사를 확정 위반 판정이 아닌 후보 진단으로 명시해야 합니다.

**N5. I13 재정의에서 기존 ‘활성 라인의 closed_qty 잔존’ 검사가 사라짐 — §8 I13**

v1의 I13c는 활성 라인에 `closed_qty > 0`이 남는 상태를 검사했습니다. v2 SQL은 이를 제거했고 I21도 대신 검출하지 않습니다. 복원 부분 실패를 놓치는 회귀이므로 기존 검사를 유지해야 합니다.

**N6. 예외 I가 ID 전체 면제이며 승인 당시 수량을 고정하지 않음 — §5-I**

`sched 151`을 통째로 제외하면 승인 이후 같은 회차의 충당이 더 증가해도 감춰집니다. `si 378`도 미충당이 100에서 증가하는 상황을 구분하지 못합니다. 이는 “같은 유형이 다시 생기면 처리”한다는 결정과 맞지 않습니다.

승인 당시 `qty·delivered_qty·충당합·차이`를 고정하고, 해당 ID에서도 기준값 변화는 신규 위반으로 반환해야 합니다. 현재 SQL에는 I 자체도 반영되지 않았습니다.

**N7. §8은 수정된 최종 점검 SQL로 실행할 수 없는 상태임**

I1a는 `... where`이며 다수 블록은 외부 v1 문서 참조입니다. I2c_under는 주석만 있고 SQL이 없으며, 예외 J도 I17 SQL에 없습니다. 이 상태로는 §4의 예외 적용 후 결과를 재현할 수 없습니다.

커밋 전에 원문을 한 파일로 합치고, 원시 검출·승인 예외·신규 위반을 구분하는 실행 가능한 SELECT를 제공해야 합니다.

### LOW

**N8. 재baseline과 최종 결정이 문서 전반에 동기화되지 않음 — §0·§4·§6·§8·§9b**

§9b는 중복 WO·취소시각 정정 후 관련 지표가 0이라고 하지만 §4와 요약은 이전 P0 2건을 현재 결과처럼 유지합니다. §6에서 확정한 I/J와 BOM P1 결정도 §0·§4·§8에 일부 이전 표현으로 남아 있습니다.

정정 전·후 측정 시각과 예외 적용 여부를 분리하고, 확정 결정에 맞춰 등급·요약·SQL 주석을 갱신해야 합니다.

**BLOCKER / HIGH**

없음.

**MEDIUM**

- **N1 잔여 — §8 묶음 4, J·I17b·I17c:** J는 해당 거래처 라인이 **하나라도** 있으면 전표 전체를 면제합니다. 혼합 전표라면 다른 거래처 라인의 ISSUE까지 제외됩니다. 또한 I17b는 `t.txn_date = s.ship_date`를 요구하지 않아, J 전표에 연결됐다는 이유로 다음 달 1~5일 범위를 벗어난 미래 원장 날짜도 숨깁니다. 거래처별 업무 규칙에 맞게 라인과 원장 날짜까지 제한해야 합니다.
- **N6 잔여 — §8 I2c_over:** `sched_id=151 AND qty=1732 AND 충당합=3748`이면 `delivered_qty`가 1,732에서 다른 값으로 바뀌어도 계속 면제됩니다. 승인 당시 `delivered_qty=1732`까지 고정해야 “값이 바뀌면 신규 위반”이라는 설명과 일치합니다.

**LOW**

- **N8 잔여 — §4.2와 §8 I2c_over:** §4는 예외 적용 후 결과라고 하면서 `sched 151`을 **1건**으로 기재하지만, §8은 그 고정값을 제외하므로 해당 행은 **0건**이어야 합니다. 원시 검출 1건·승인 예외 1건·최종 위반 0건으로 구분하면 됩니다.

**REQUIRED TESTS**

위 조건 수정 후 §8 네 묶음을 읽기 전용으로 재실행하여 §4와 대조하십시오. 특히 sched 151의 delivered 변경, 혼합 거래처 전표, J 전표의 납품일과 다른 미래 원장 날짜가 제외되지 않는지 확인이 필요합니다.

**REVIEW LIMITATIONS**

정적 검토이며 운영 baseline과 PostgreSQL 실행 성공은 독립 검증하지 않았습니다. 이전에 수용했고 변경되지 않은 항목은 재지적하지 않았습니다.
