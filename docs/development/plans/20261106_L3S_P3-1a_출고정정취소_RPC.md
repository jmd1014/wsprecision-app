## 4. 제안 구조 (P3-1a)

### 4-1. 원칙
1. **되돌림(감소·취소)은 서버가 계산한다.** 근거(충당 행, ISSUE 원장)가 전부 DB 에 있다. 화면은 "어느 라인을 얼마로"만 보낸다.
2. **증가분은 확정과 같은 방식(화면이 계획, 서버가 검증)으로 한다.** 회차 충당·LOT 선입선출 규칙을 SQL 로 한 벌 더 만들지 않는다.
3. **전부 아니면 전무.** 실패하면 전체 롤백.
4. **불변식이 안 맞는 옛 데이터는 추정으로 처리하지 않고 거부한다**(§7, 결정 2). 그래서 "경고만 내고 진행"하는 경로가 없어진다 — 남는 것은 정보성 안내뿐이다.
5. **재실행 안전.** `request_id` 로 같은 요청의 두 번째 호출을 구분하고, 내용이 다르면 거부한다.
6. **화면이 먼저 막고 서버가 다시 막는다.** 거부 사유는 같은 SQL 한 곳에서 판정한다(§4-5).

### 4-3. 처리 순서

**① 전표 잠금 → 재실행 판정**
- `shipments` 행 `FOR UPDATE`.
- 이 전표의 `shipment_revisions` 에 같은 `request_id` 가 있으면: 저장된 action·라인별 (si_id, 전·후 수량)이 이번 payload 와 **같으면** 쓰지 않고 `{ok: true, replayed: true, rev_no: <그 이력의 rev_no>, info: <저장된 안내>}` 반환. **다르면** `request_conflict` 거부. 재실행은 나머지 잠금을 잡지 않는다.

**② 나머지 잠금 — 값 읽기와 잠금을 같은 SELECT 로**
전표의 전 라인 → 영향받는 수주들의 **전 라인**(soi 오름차순 `FOR UPDATE`) → 영향 수주 라인들의 **전 회차**(sched 오름차순) → 증가 라인의 제품 advisory(product 오름차순, 069 와 같은 키, `allow_over` 와 무관하게) → 영향 수주 머리글(so 오름차순 `FOR NO KEY UPDATE`).
- 수주의 전 라인을 잠그는 이유(data H1): 069 의 머리글 재집계는 한 문장 안에서 집계와 갱신을 같이 해, 정정이 끝난 뒤 깨어난 확정이 옛 집계로 머리글을 덮어쓸 수 있다. 전 라인을 잡으면 형제 라인의 확정이 수주 라인 잠금에서 기다리게 되어 그 창이 닫히고, 머리글 잠금 순서 문제(확정 전표 98장 중 56장이 다중 수주)도 같이 없어진다. `so_close_lines` 와 같은 방식이고 전역 soi 오름차순이 유지된다.
- 잠금 전에 읽은 값을 다시 쓰지 않는다(D16 재발 방지).

**③ 전제 검사**(어긋나면 거부, §4-4)
- 상태 = CONFIRMED. `rev_no` = `expected_rev_no`. 사유 있음.
- 월 마감: `to_char(ship_date, 'YYYY-MM')` 이 `sales_month_close` 에 있으면 거부.
- CONFIRMED 인데 CANCEL 이력이 있으면 거부(옛 부분 취소 상태).
- EDIT: `lines` 비었음 / 이 전표 라인 아님 / 중복 / `qty_before` ≠ 현재 수량 / `qty_after` < 0 / 변화 없음 → 거부. **수량 > 0 인 라인을 전부 0 으로 만드는 EDIT 는 거부**하고 취소로 안내(`use_cancel`).
- 데이터 사유(§4-5): 대상 라인에 `legacy_no_alloc`·`issue_mismatch`·`round_short`·`recv_underflow` 가 하나라도 있으면 거부. EDIT 는 **바뀌는 라인만**, CANCEL 은 수량 > 0 인 전 라인을 본다.

**④ 감소분 — 서버 계산, 라인 si 오름차순으로 한 줄씩**(집합 UPDATE 금지 — 두 라인이 같은 회차·같은 수주 라인을 공유할 수 있다)
1. 수주 라인(수주 연결 라인만): `received −= q`. ③ 에서 `received ≥ q` 를 확인했으므로 0 하한에 걸리지 않는다. 상태 규칙 = `revise_line_fields`:
   - 활성 → `pending = GREATEST(qty − received, 0)`, 상태 재계산.
   - 비활성(CLOSED·CANCELLED·REPLACED) → received 만, pending 0, 상태 유지, CLOSED/CANCELLED 는 `closed_qty = GREATEST(qty − received, 0)`.
   - 머리글이 종결·취소(`CLOSED`·`CANCELLED`·`CANCELED`)면 라인 상태와 무관하게 비활성 취급(D15). 이 정정으로 처음 닫히는 라인(`closed_rounds` 가 비어 있음)은 **그 수주 라인의 회차를 환원하기 전 값**으로 `closed_rounds = [{sched_id, qty_before, delivered}]`(sched 오름차순), `close_reason = '출고 정정 SH-…'`.
2. 회차 환원: 이 라인의 충당 행을 회차 납기 최근순(동률은 alloc_id 오름차순)으로 `min(충당 수량, 남은 수량)` 만큼 줄이고 회차 `delivered_qty` 도 같은 만큼 줄인다(`updated_at` 갱신). ③ 의 `round_short` 검사로 `delivered ≥ 줄일 수량` 이 보장된다. 충당이 0 이 되면 행 삭제. 충당이 라인 수량보다 적어 남는 수량은 **미충당분**이다 — 회차는 그대로 두고 안내(`unallocated`)만 남긴다.
3. 닫힌 채 남는 라인은 `qty > delivered` 인 회차를 `qty = delivered` 로(077 규칙).
4. LOT 복원(제품 연결 라인만): 이 라인의 ISSUE 원장을 LOT 별 순합으로 보고 마지막에 차감된 LOT 부터 양수 ISSUE 행 추가. ③ 의 `issue_mismatch` 검사로 순합 = 라인 수량이 보장되므로 남는 수량이 없다. LOT NULL 은 `IS NOT DISTINCT FROM` 으로 한 LOT 처럼 다룬다.
   - 복원 행: `product_id`·`unit`·`work_order` 는 원 ISSUE 행 기준(`work_order = lot_number`), `txn_date` = **KST 오늘** `(now() AT TIME ZONE 'Asia/Seoul')::date`, `remark` = 옛 엔진과 글자 단위로 같게(`출고 취소 SH-…: 수주번호 (사유)`, 수주번호 없으면 `-`), `created_by` = who. 본문에 `CURRENT_DATE` 를 쓰지 않는다.

**⑤ 증가분 — payload 검증 뒤 적용**
- 증가는 **수주·제품이 모두 연결된 라인만**(아니면 `line_unlinked`).
- `expected_received_before` 는 ② 에서 읽은 **감소 적용 전** 값과 비교(아니면 `stale`).
- 비활성 라인·비활성 머리글 → `line_closed`. `over_pending`·`sched_over`·재고 검사는 **감소 적용 뒤** 값으로.
- 회차·충당·ISSUE: 069 ⓓ-2~4 와 같은 검사. ISSUE 행의 `txn_date`(KST 오늘)·`remark`(LOT 없는 행은 뒤에 ` (LOT 미지정)`)·`created_by` 는 서버가 채운다.
- 회차에 못 실은 증가분은 069 처럼 `unallocated` 로 돌려준다.
- 화면의 증가 계획은 같은 요청의 감소(회차 여유, 복원된 LOT 잔량)를 먼저 반영한 상태로 세운다 — `plan_revision` 이 처리.

**⑥ 전표 라인 수량**: EDIT → `qty_after`. CANCEL → 그대로.

**⑦ 이력**: 라인마다 1행(`rev_no = expected + 1`, action, si_id, **pn**, 전·후 수량, 사유, 처리자, `request_id`, `info`). CANCEL 인데 수량 > 0 라인이 하나도 없으면 **머리글 이력 1행**(si_id NULL, 0 → 0)을 쓴다 — 재실행 판정과 "취소 전표에는 CANCEL 이력" 불변식을 위해.

**⑧ 수주 머리글**: 활성 라인만 재집계(069 ⓔ-4 와 같은 식). 비활성 머리글 무접촉.

**⑨ 전표 머리글**: `rev_no + 1`, `revised_at`. CANCEL 이면 `status = CANCELLED`, `cancelled_at`, `cancel_reason`.

**⑩ 사후 조건**(어긋나면 RAISE — 전체 롤백): CANCEL 이면 이 전표 전 라인의 충당 0행 · 라인별 ISSUE 순합 0. 영향 수주 라인마다 `received + pending + closed = qty`(활성은 closed 0).

반환: `{ok, replayed: false, action, rev_no, lines, restored_txns, released_allocs, inc_allocs, inc_txns, so_ids, info: [{si_id, kind: "unallocated", qty}]}`.

### 4-5. 데이터 사유 — 한 곳에서 판정(`revise_shipment_check` 와 공용)

| 코드 | 판정 | 지금 운영 |
|---|---|---|
| `legacy_no_alloc` | **고정 목록** si_id ∈ {4, 10, 16, 17, 23, 36, 48, 60, 63, 78, 99, 148, 176} **이고** Σ충당 < 라인 수량 | 13라인 · 전표 10장(2026-08-10 ~ 09-09) |
| `issue_mismatch` | 제품 연결 라인의 ISSUE 순합 ≠ 라인 수량 | 6라인 · 전표 3장(si 35·37 / 330·331 / 337·340 — 같은 수주 라인을 두 줄로 낸 전표에서 차감이 한 줄에 몰림) |

- 고정 목록을 쓰는 이유: "충당 0행 + 회차 있음"이라는 구조 조건은 회차가 다 차서 전량 미충당으로 확정된 새 라인, 감소 정정으로 충당이 다 풀린 라인과 구분되지 않는다. 목록 밖의 충당 0행 라인은 **회차 변동 없음 + 미충당 안내**로 정상 처리한다. 목록 안 라인도 건별 정정으로 충당을 채우면 조건(Σ충당 < 수량)에서 빠져 자동으로 통과한다.
- 세 전표군을 합치면 **전표 12장**이다(중복 제외): SH-20260810-01, 0812-01, 0812-02, 0817-01, 0819-01, 0821-01, 0824-02, 0831-01, 0907-01, 0909-02, 0923-02, 0929-01.
- EDIT 는 해당 라인이 바뀌는 라인에 들어 있을 때만 거부한다 — 같은 전표의 다른 라인 정정은 통과.
- 화면: 전표를 열 때 `revise_shipment_check` 로 미리 판정해 해당 라인·버튼을 잠그고 안내를 먼저 보여 준다. 안내에 들어갈 것 = 전표번호와 해당 라인(품번·수주번호·수량), 이유, 아무것도 바뀌지 않았다는 것, 할 수 있는 것(다른 라인 정정), 관리자에게 전달할 것(전표번호·원하는 결과·사유).
- 건별 정정 절차서(L3-D 틀: 옛 추정 규칙 + 차감 재배치 SQL 틀)를 이 묶음에서 같이 쓴다.

### 4-6. 호출부 상태 기계(응답 불명, P3-0 과 같은 원칙)
1. 호출 전에 **진행 중 기록**을 세션에 남긴다: 전표, `request_id`, 계획. 확정 결과(성공·거부)가 나올 때만 지운다. 남아 있으면 다음 렌더에서 3 을 한다.
2. 결과 분류: `ok` → 성공 / P0001 거부 → 거부(쓰기 없음 확정) / 전송 오류·비정상 본문(None, `{}`, `ok` 아님)·40P01·55P03·57014 → **불명**.
3. 한 번이라도 불명이 나오면: 대기 뒤 같은 `request_id` 로 재호출(횟수·간격은 P3-0 값). 마지막까지 `ok` 가 아니면 — 그 사이 거부가 나왔더라도 — `shipment_revisions` 를 `shipment_id + request_id` 로 **캐시 없이** 재조회한다. 있으면 성공 안내(알림 1회), 없으면 "반영 여부를 확인하지 못했습니다" 로 끝낸다("반영되지 않았습니다" 라고 쓰지 않는다). 옛 경로로 넘어가지 않는다.
4. 함수 없음(`RpcUnavailable`) → 차단 문구, 쓰기 없음.
5. 성공·재실행 뒤: `mr_cache` 비우기, EDIT 는 `ship_open_no` 유지, `clear_cache`, 안내(`info` 포함)는 `nav_flash` 로 rerun 뒤에 보이게, 알림 1회. 불명으로 끝나면 알림 없음.
6. `request_id` 수명: EDIT 는 [정정 적용] 클릭 때 만들어 `cf_rv_plan` 에 `shipment_id`·`rev_no` 와 함께 넣는다(다시 누르면 새 값). [실행 확정] 때 계획의 전표·rev 가 현재 선택과 다르면 버린다. CANCEL 은 [전표 취소] 클릭 때 만들어 전표별 확인 플래그 값으로 둔다. 정정 확인 창도 취소처럼 **전표 단위 scope** 로 바꾼다. "계획이 없으면 현재 위젯 값으로 대체"는 없앤다.
7. 화면 가드: CONFIRMED 인데 CANCEL 이력이 하나라도 있으면 정정·취소 **둘 다 잠금** + 관리자 안내(지금의 "취소 재개" 안내는 삭제). 월 마감 화면 선차단·사유 필수·확인 창·`click_guard` 는 유지.
