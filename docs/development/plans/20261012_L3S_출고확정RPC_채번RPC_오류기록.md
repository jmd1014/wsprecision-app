## 공통 전제 — `db.py` RPC 헬퍼 [v2 전면 수정]

`app/db/supabase_rest.py` 의 기존 `rpc`(모든 비-2xx 를 RuntimeError, 404 구분 없음)와는 **별도 구현**이다.

```
class RpcUnavailable(Exception)        # 서버가 함수를 실행하지 않았음이 확실: HTTP 404 + PostgREST code PGRST202
class RpcRejected(Exception)           # 함수가 RAISE 로 거부(HTTP 400, code/message 있음) → 미반영 확정, 재시도 가능
class RpcTransportError(Exception)     # Timeout / ConnectionError / 5xx / 본문 없음 → 반영 여부 불명
def rpc(name, params, timeout=(5, 30)) -> dict | list
```
- 성공은 **JSON 본문이 있을 때만**. 본문이 비면 `RpcTransportError`.
- `RpcRejected` 와 성공 뒤에는 `clear_cache()`(거부 원인이 오래된 화면이므로).
- `RpcUnavailable` 은 `log_error(kind='rpc_fallback')` 로 반드시 기록 — 파라미터 이름 불일치도 PGRST202 로 나오므로 "RPC 가 한 번도 안 돌았는데 아무도 모르는" 상태를 막는다(Data A-H3).
- 테스트 mock(`db.rpc = lambda *a, **k: None`) 호환: 앱은 **None 을 "호출 결과 불명"** 으로 다룬다. 출고 확정(A)은 None 이면 머리글 재조회 + 흔적 검사를 **다시** 한 뒤 깨끗할 때만 기존 경로로 폴백(QA BLOCKER A-B1). 채번(B)은 카운터 갱신 외 부작용이 없으므로 None 이면 바로 폴백.
- 기존 출고 테스트 fixture(`tests/test_bulk_delivery.py::ship_db`, `tests/test_shipment_revision_flow.py::rev_db`)는 `rpc` 를 patch 하지 않아 실제 HTTP 를 치게 된다(QA A-H1) → fixture 에 `rpc=None`·`log_error=no-op` patch 추가 + `conftest.py` autouse 로 실제 `requests.*` 호출 시 즉시 실패하는 가드.
