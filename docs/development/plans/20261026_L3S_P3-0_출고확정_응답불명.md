# P3-0 — 출고 확정 응답 불명(RPC 전송 오류) 처리 계획서 **v2** (2026-10-26, 기획·검토 세션)

로드맵 ID: **P3-0 [예외 HIGH]**. 등급 **L3-S**(출고 확정 = 수주 납품·회차·충당·완성 재고 원장 쓰기). 근거: `_안정화로드맵_검토보고서_20261021.md` §9(기획 세션의 "해소됨" 판정 철회), ROADMAP v1.3 P3-0, `streamlit_app.py` 10693~10800(현행), `db.py` 436~512(`rpc`), `supabase/migrations/076_so_close_rpc.sql`(confirm_shipment v4 본문). 마이그레이션 **없음**(RPC 본문 변경 없이 호출부만).

## 1. 문제 (현행 코드 그대로)

출고 확정은 RPC `confirm_shipment`(한 트랜잭션)로 반영한다. 응답이 **ok** 면 끝, **거부(RpcRejected)** 면 중단, **함수 없음(RpcUnavailable)** 이면 기존 6단계 경로. 문제는 **전송 오류(RpcTransportError: timeout 30초·연결 끊김·5xx·본문 없음)** = "반영 여부 불명" 상태다(10745~10773):
1. 캐시를 비우고 전표 머리글 `status` 와 흔적(충당·ISSUE)을 **한 번** 읽는다.
2. 머리글이 DRAFT 이고 흔적이 없으면 **기존 6단계 경로를 실행**한다(`_cf_legacy = True`).

틈: PostgREST 가 30초 뒤 클라이언트 연결을 끊어도 **DB 쪽 함수는 계속 실행되어 뒤늦게 커밋**될 수 있다(늦은 커밋). 1 의 조회 시점에는 아직 DRAFT·흔적 없음 → 2 의 6단계가 돌아가 **같은 전표가 두 번 반영**(납품·회차·충당·완성 재고 이중 차감)된다. 6단계 경로는 트랜잭션이 아니라 중간 실패도 남긴다. 발생 빈도는 낮지만(전송 오류 × 늦은 커밋 × 같은 순간), 결과가 운영 수량 오염이라 HIGH.

## 2. 목표·원칙

- **응답 불명이면 기존 경로를 절대 쓰지 않는다.** 6단계 경로는 `RpcUnavailable`(함수 없음)에만 남긴다(P3-6 에서 제거).
- 불명 처리는 **재조회 대기 → RPC 재호출** 로 끝낸다. 재호출은 안전하다: 함수 첫머리의 `shipments FOR UPDATE` 잠금이 아직 실행 중인 1차 호출과 직렬화되고, 1차가 커밋됐으면 `not_draft`/`already_applied` 로 거부되며, 1차가 롤백됐으면 2차가 정상 반영한다. 즉 **"늦은 커밋"은 2차 호출의 거부로 드러난다.**
- 두 번째도 불명이면 **중단**하고 사용자에게 "화면 새로고침 → 전표 상태 확인"을 안내한다(자동 3차 금지).

## 3. 설계

### 3-1. 호출부 상태 기계 (`_cf_confirm_via_rpc(shipment_id, payload)` 헬퍼로 분리, 10693~10773 대체)

| 단계 | 동작 | 결과 |
|---|---|---|
| ① 1차 호출 | `db.rpc("confirm_shipment", …)` | ok → 완료 / Rejected → 중단(현행 문구) / Unavailable → 6단계(현행, 기록) / **Transport → ②** |
| ② 재조회 대기 | `clear_cache()` → 전표 `status` 읽기. DRAFT 가 아니거나 흔적(충당·ISSUE)이 있으면 **"늦은 커밋 확인"** → 완료로 처리(ok 와 같은 후처리, `_rpc_res` 없으므로 `sois = len(plan)`, skipped 는 재조회로). DRAFT·흔적 없음이면 2초 뒤 한 번 더 읽고(총 2회, ~2초) 그래도 깨끗하면 ③ | 확인/③ |
| ③ 2차 호출(재시도 1회) | 같은 payload 로 `db.rpc` 재호출 | ok → 완료 / **Rejected 중 `not_draft`·`already_applied`·`stale`** → 1차가 그 사이 커밋 → ② 와 같이 재조회로 확인 뒤 완료 / 그 밖의 Rejected → 중단(문구) / Unavailable → 중단(이 시점의 Unavailable 은 모순이므로 6단계 금지) / **Transport → ④** |
| ④ 중단 | `st.error("출고 확정 응답을 두 번 받지 못했습니다 — 반영됐을 수 있습니다. 화면을 새로 고쳐 전표 상태를 확인한 뒤, 아직 작성중이면 다시 확정하세요.")`, `log_error("rpc_unknown", …)` 2회 기록, `click_guard` 해제 | 사용자 재진입 시 ①부터 — 1차·2차가 뒤늦게 커밋됐으면 거부로 드러남 |

- `_cf_legacy` 는 **`RpcUnavailable` 1차에서만** True. 그 외 경로에서 True 가 되는 코드 삭제. 정적 테스트로 고정.
- 타임아웃: `db.rpc` 기본 (5, 30) 유지. 2차 호출도 같은 값.

## 4. 위험
- 2차 호출이 1차의 잠금을 기다리다 30초 timeout → ④. 이 경우 1차는 결국 커밋 또는 롤백되므로 사용자가 새로고침 뒤 다시 누르면 수습된다. 자동 3차는 하지 않는다.
- 목 DB 는 잠금을 흉내 내지 못한다 — T3 는 "2차 때 거부" 로 모사. 실제 직렬화는 운영 드라이런 1회로.
- 6단계 경로를 Unavailable 에 남기는 것은 P3-6 까지의 한계(함수가 지워질 일은 없음).

### 3-1 v2 상태 기계 (최종)
