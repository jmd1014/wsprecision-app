## 2. 왜 사이드바 2단인가

- **로딩 시간**: `st.tabs` 는 탭 하나만 보여도 모든 탭 본문을 매번 실행한다. db.py 실측(2026-09-17): 화면 시간의 95% 가 DB 왕복(화면당 20~30회 × 약 240ms). 세부 메뉴로 바꾸면 선택한 화면 본문만 실행된다. 저장 직후에는 db.py 가 캐시 전체를 비우므로 지금은 저장 한 번에 그 페이지 모든 탭 조회가 다시 나간다. 예: 출고 관리의 '완성 재고'(조회 3)를 보려면 지금은 '출고 전표'(조회 26 + 내부 함수 8)까지 매번 함께 실행된다.
- **사용성**: 어느 화면에서든 세부 화면까지 한 번에 이동. 메인을 바꿨다 돌아와도 마지막 세부 화면 유지. 현재 위치가 사이드바에 표시.
- **대가(이번 계획이 막아야 하는 것)**: 탭은 브라우저 안에서만 바뀌어 입력값이 그대로였지만, 세부 메뉴 전환은 다시 실행(rerun)이고 **그려지지 않은 위젯 값은 Streamlit 이 지운다**(§5-3). 또 탭 바는 휴대폰에서도 본문에 있었지만 사이드바는 열어야 보인다(§4-4).

## 3. 범위

**이번 단계**
- 사용자 영역 6개: 홈(세부 없음), 수주 관리(3), 구매 관리(6), 생산 계획(4), 공정 관리(5), 출고 관리(4) → 탭을 세부 메뉴로. 이름·순서는 지금 탭 그대로.
- 출고 전표 취소 확인 게이트 결함 수정(§5-2, 지금도 같은 탭 안에서 전표를 바꿔 선택하면 생길 수 있는 기존 결함).

**하지 않는 것**
- 관리자 영역 4개(마스터 관리 9탭, 원가 확인 7탭, 생산 보고 5탭, 영업 보고 3탭)는 지금처럼 메인 + 탭(D4). 사이드바 관리자 구역에 메인 항목으로만.
- **URL 동기화(`st.query_params`)는 이번에 하지 않는다** — 로그인·쿠키 왕복·공용 태블릿 로그아웃과 얽혀 위험이 큼(UX·QA). 즐겨찾기 단계에서 같이 설계.
- 메뉴 이름 변경·재배치·화면 통합, 즐겨찾기, DB 변경.

    발주 제안

### 4-2. 구현 방식

- **메뉴 코드는 `streamlit_app.py` 안에 둔다. 폴백 없음**(QA H-2: 탭을 없앤 뒤 '옛 라디오 메뉴' 폴백은 세부 화면으로 갈 수 없어 의미가 없다. 새 모듈 import 실패 위험(10/14~15 핫픽스 유형)도 없앰).
- 메뉴 정의 한 곳: `NAV = [("home", "홈", []), ("so", "수주 관리", [("input","새 수주 입력"), ("list","수주 목록"), ("sched","납품 스케줄")]), ...]` — **위젯 키는 ASCII 고정 키**(`nav_m_so`, `nav_s_so_list`), 화면에 보이는 이름은 한글. 관리자 `NAV_ADMIN` 은 세부 없음.
- 상태(일반 세션 키, 위젯 키 아님): `nav_page`(메인 키), `nav_sub`(dict: 메인 키 → 세부 키, 메인별 마지막 세부 기억). 기존 `page`(한글 메인 이름) 변수는 그대로 만들어 아래 `if page == …` 분기를 바꾸지 않는다. 작업자 계정이 관리자 메인 상태면 홈(지금 1495 와 같은 효과).
- `nav_sub_of(page)`: NAV 에 없는 값이면 첫 세부로 보정(QA M-1).
- **사이드바 항목은 `st.button(..., on_click=콜백)`** 으로(UX H-3). `if st.button(): …; st.rerun()` 금지 — 강조가 한 박자 늦고 무거운 실행이 한 번 더 돈다. `type="primary"`(파란 채움)는 '확정' 버튼과 헷갈리므로 쓰지 않는다.
- 스타일: 전역 버튼 CSS(95~112, 회색 면·가운데 정렬)를 사이드바 메뉴 키에만 덮어쓰기 — 왼쪽 정렬, 투명 배경, 세부 항목 들여쓰기·작은 글씨, 선택 항목은 연한 주색 배경 + #1b64da 글자 + 왼쪽 막대. 토큰은 상단 CSS 블록 한 곳(CLAUDE.md 디자인 시스템), 이모지 금지.
- **화면 이동은 함수 하나로**: `nav_go(main_key, sub_key, flash=None)` — 콜백 안에서 nav 상태를 바꾸고, 필요하면 다음 실행에 보여줄 안내(flash)를 남긴다. 본문의 모든 자동 전환은 이 함수만 쓴다(기존 `sch_view_next` 7601 패턴).
- 메뉴(메인 또는 세부)가 바뀌는 실행에서 **`cfm_*` 키 전부와 `cf_rv_plan` 을 지운다**(§5-2).
- 페이지 안: `a, b, c = st.tabs([...])` → `_sub = nav_sub_of(page)`; `with a:` → `if _sub == "<세부 키>":` (들여쓰기 그대로). 기존 `st.subheader`(5589, 8321, 10636, 12533, 16315)를 **"구매 관리 › 입고 처리" 제목 줄로 교체**(새 줄 추가 금지 — 상단 헤더 352와 겹침).
- 오류 기록 `_err_ctx`(1499)의 page 에 세부 이름 포함("구매 관리 › 입고 처리"), 조회 프로파일 비교도 세부 단위(UX M-8).
- 로그아웃(1517)에서 `nav_page`·`nav_sub`·`_NAV_KEEP` 값을 비운다 — 공용 태블릿에서 다음 사람이 앞사람 화면·입력값으로 시작하지 않게.

### 4-3. 규칙

- **"탭 안·세부 화면 안 `st.stop()` 금지" 유지**(Data M3: 실행 끝 블록 22474~22505 — '처리 중' 표시 해제, 조회 상한 경고 `_fetch_truncated` — 이 건너뛰어진다). CLAUDE.md 문구는 "탭 안" → "탭·세부 화면 안"으로 갱신.

### 4-4. 휴대폰·태블릿

- 직접 만든 사이드바 버튼은 눌러도 오버레이 사이드바가 닫히지 않아 세부 이동마다 "열기 → 선택 → 닫기"가 된다(UX H-2).
- **본문 제목 줄 바로 아래에 세부 선택 가로 컨트롤**(`st.segmented_control`, 없으면 horizontal radio)을 둔다. 상태는 같은 `nav_sub` 를 on_change 콜백으로 맞춘다(위젯 키는 별도 ASCII 키). **좁은 화면에서만 보이고 넓은 화면에서는 CSS(`.st-key-…` + media query)로 숨긴다** — 데스크톱은 사이드바가 주 메뉴(D1). 숨김 클래스가 동작하지 않는 버전이면 항상 보이게 둔다(기능상 문제 없음). 수주 관리는 공통 패널(5589~6188)이 길어 이 컨트롤을 패널 **위**에 둔다.

### 5-2. 출고 전표 취소 확인 게이트 (기존 결함, 이번에 함께 수정)

- 현상: `cfm_cf_cancel`(9542, 10208)·`cfm_cf_cancel_empty`(9360)가 전표 id 와 묶여 있지 않다. 전표 A 에서 [전표 취소] → 확인창 상태로 다른 전표 B 가 선택되면(세부 이동 후 `cf_grid` 선택 소멸 → 첫 행, 또는 `ship_open_no` 로 순서 변경, 지금도 같은 탭 안에서 다른 전표 선택 시) **B 에 대한 확인창이 바로 뜬다**. 확정 전표 취소 실행 조건(9543)은 사유(`_cx_reason`, 전표별 키)를 다시 확인하지 않아 **사유 없이 B 전체가 역반영될 수 있다**.
- 수정: (1) 게이트 키에 shipment_id 포함(`cf_cancel_{id}` → `cfm_cf_cancel_{id}`), (2) 9543 조건에 `and _cx_reason.strip()`, (3) 메뉴 전환 시 `cfm_*`·`cf_rv_plan` 일괄 삭제(§4-2). 정정(`cf_rv_plan`)은 si_id 기준이라 다른 전표에서는 변경 없음으로 처리돼 안전(utils/shipment_adjust.py:114) — 그래도 같이 지운다.
- 이 수정은 메뉴 개편과 독립이므로 **먼저 별도 커밋**으로.

### 5-3. 세부 화면을 옮겨도 유지할 입력값 (`_NAV_KEEP`)

- 원리: 그려지지 않은 위젯 키는 그 실행 끝에 지워진다. 지금은 탭이 모두 그려져 값이 남았다.

### 13-2. D7 발주 제안 → 발주서 작성 안의 모드 (커밋 2)

**결정 근거**: 발주 제안(부족 자재 확인 → 거래처별 담기)과 발주서 작성은 구매 담당의 한 흐름이고, 같은 계산(`_mr`)을 쓴다. 발주서 작성 화면에는 이미 '발주 필요' 열(14225 부근)이 있다. 생산 쪽은 아직 이 화면을 쓰지 않는다(사용자 확인 2026-10-19). 구매 관리 세부 메뉴 6 → 5.

**방식 — 위아래로 붙이지 않고 모드 전환** (검토 세션 판단):
- 발주서 작성 화면 맨 위(제목 줄 아래)에 모드 전환 **[부족 자재에서 담기] / [발주서 편집]** (`st.segmented_control`, 없으면 horizontal radio; 상태 키는 일반 세션 키 `po_mode`, 위젯 키는 별도 ASCII).
- **선택한 모드의 코드만 실행**한다. 이유: 발주서 편집은 표 한 칸 고칠 때마다 다시 실행되는 화면이라, 제안 블록(조회 3~5회 + 목록)을 같이 그리면 편집할 때마다 느려진다. 접어두기(expander)는 안쪽 코드가 그대로 실행되므로 해결책이 아니다.
- 기본 모드: `po_items`(담긴 품목)가 있으면 **발주서 편집**, 없으면 **부족 자재에서 담기**. 이후에는 마지막 모드 기억(`_NAV_KEEP` 대상).
- '부족 자재에서 담기' 모드 = 지금의 발주 제안 화면 그대로(B1 블록, '제품별 자재 필요량 — 제안의 근거' 펼치기 포함). 거래처별 **[발주서 작성]** 버튼(`go_po_<거래처>`)은 화면 이동(`nav_go`) 대신 **콜백에서 `po_mode` = 편집 + `po_prefill_*` + `po_bucket` 설정**(C1 과 같은 규칙: `po_vendor` 는 세션 API 로 넣지 않고 지움, 선택은 prefill 이름으로 `index=`).
- 발주 이력 '복사해서 수정'(`po_copy_<id>`)은 `nav_go("po","new")` + `po_mode` = 편집.
- NAV 에서 `("sug","발주 제안")` 제거. 옛 상태(`nav_sub["po"] == "sug"`)는 `nav_sub_of` 보정으로 `new` + 모드 '부족 자재'로.
- B2 조건: `_mr_compute` 는 세부 = 발주서 작성일 때만(두 모드 모두 `_mr` 사용 — 부족 자재 모드는 목록, 편집 모드는 '발주 필요' 열). B1 블록은 '부족 자재' 모드 분기 안.
- `mr_cache` 무효화 지점(§5-4)은 그대로.

**테스트 변경**
- §6-2 7: `go_po_<거래처>` 클릭 → 같은 화면에서 모드 = 편집, `po_items` 수 = 부족 자재 수, `po_bucket` = 거래처 그룹, Session State 경고 없음. `po_copy_<id>` → 세부 = 발주서 작성, 모드 = 편집.
- §6-2 8: `_mr_compute` 호출 — 발주 이력·입고 처리·입고 현황·매입 등록 0회, 발주서 작성(어느 모드든) 첫 진입 1회, 5분 안 모드 전환 추가 0회.
